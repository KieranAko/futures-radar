# 理论库（Theory Base）

> 本目录是 futures-radar 的**独立思想层**：它不属于 FinCoT 推理链，也不属于策略库，
> 而是项目推进遇到阻碍时回查参考的理论根基。
>
> 本阶段（理论库建设阶段）只做三件事，且只做这三件事：
> 1. **精读吸收**——把一套理论的主干逻辑完整吸收进来；
> 2. **自洽性检验**——检验该理论内部逻辑是否自洽（前提充分、推论闭环、边界一致）；
> 3. **项目相关性检验**——检验该理论在哪些层面与 futures-radar 相关，相关到什么程度。
>
> 理论库**不含运行建议**。是否、何时、如何把某个思想应用到项目，是未来在具体
> 阻碍面前的设计决策，不属于本阶段产出。

## 使用规则

**核心工作流（遇到问题时的标准路径）：**

```
遇到问题，没有解决方案
  → 先停下，写清楚问题是什么（问题陈述）
  → 查询理论库，按"视角"定位相关报告（流程/内容/结构/来源）
  → 找到与该问题对应的理论命题、边界或诊断（记录报告编号 + 章节 + 命题）
  → 基于理论依据设计解决方案（设计逻辑显式引用理论，不盲目推导）
  → 队长确认后实施
```

**规则：**

1. **查库优先于推导**：问题有理论对应时，必须先回查理论库再设计方案；
   禁止在没有理论依据的情况下自行拍脑袋推导（阈值、持有期、流程、架构同理）。
2. **无依据时的两条路**：理论库查不到对应依据时——
   a. 若问题属于理论空白，先扩充理论库（新增吸收报告），再回头设计；
   b. 若问题属于纯工程/编码问题（与交易理论无关），明确标注为工程问题，不走理论路径。
3. **记录引用**：每次应用设计都记录"参考了哪份报告哪一节哪条命题"，
   使方案可回溯、可复核。
4. **不自动落地**：本库的任何思想不自动改变代码、FinCoT、策略库或流程；
   每次应用都是一次独立设计决策。
5. **扩充纪律**：新增条目必须同时完成精读吸收、自洽性检验、项目相关性检验三部分；
   宁缺毋滥，同类理论只保留更完整的一个。
